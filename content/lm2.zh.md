## 模型看不到字,只看到编号

在任何文本进入模型之前,它先被切成 token,再被换成整数编号。**模型的整个世界就是这串整数。** 它从来没有见过字母,也不知道「strawberry」这个词是由哪些字符组成的——它看到的可能是 `[496, 675, 15717]` 这样三个不透明的数字。

这个事实解释了一大批看起来很怪的现象,我们后面会挨个对上。

## 为什么不按字,也不按词

有两个显而易见的方案,都不好用:

**按字符切**。词表极小(几千个),没有未知词问题。但序列会变得非常长——同样一句话的 token 数是按词切的四五倍,而注意力的代价随长度平方增长。更麻烦的是,模型要先花掉相当一部分容量去学「字符怎么组成词」这件人类不需要它学的事。

**按词切**。序列短,语义单元清晰。但词表会爆炸(英文加上各种变形、专名、拼写错误,几十万都不够),而且永远会遇到没见过的词——一个词表外的产品名就只能变成 `<UNK>`,信息全丢。

**子词切分**是这两者之间的折中,也是今天所有主流模型的做法:常见词是一个完整 token,罕见词被切成几个有意义的片段,任何字符串都能被表示,词表控制在几万到二十万之间。

## BPE 是怎么建出词表的

字节对编码(BPE)的训练过程简单到可以手算:

1. 初始词表就是所有单字节(或单字符)。
2. 统计语料里所有相邻符号对的出现频率,把最频繁的那一对合并成一个新符号,加入词表。
3. 重复第 2 步,直到词表达到目标大小。

举例:如果语料里 `l` 和 `o` 经常相邻,`lo` 就会被合并;后来 `lo` 和 `w` 又经常相邻,`low` 就成了一个 token。**所以词表里的 token 不是语言学单位,而是统计上的高频片段。** 这也是为什么同一个词在不同位置可能被切得不一样,以及为什么带前导空格的 `" the"` 和不带的 `"the"` 通常是两个不同的 token。

## 分词带来的四类真实后果

**一,数不清字母。** 「strawberry 里有几个 r」这个著名的失败不是因为模型笨,而是因为它看到的是几个整数,里面没有字母信息。同理它不擅长反转字符串、数字符数、处理字谜。

**二,数字算不准。** 长数字被按几位一组切开,`1284736` 可能变成 `128|473|6`。模型于是要在这种碎片化表示上学会进位——它能学到一定程度,但比人类用竖式差远了。这是给它一个计算器(工具调用)几乎总是更好的原因。

**三,不同语言的成本差好几倍。** 词表是按语料统计建的,而主流语料以英文为主。所以同样的信息量,中文、日文、泰文的 token 数常常是英文的一到两倍,阿拉伯语和一些小语种更糟。这直接乘在你的 API 账单上——你可以在上面的实验里切换样例亲眼看到差距。

**四,代码被切得很碎。** 缩进、下划线、驼峰命名、括号嵌套都会产生大量 token。一个 200 行的文件轻松吃掉几千 token。

## 嵌入:从编号到向量

token 编号本身没有任何语义(编号 500 和 501 毫无关系)。真正的语义来自**嵌入矩阵**:一个 `词表大小 × hidden` 的查表矩阵,每个 token 编号对应一行向量。

这个矩阵很大。词表 128K、hidden 4096 时,它有 5.2 亿个参数——在一个 7B 模型里占了 7% 以上,而输出层通常还要一份同样大小的(有些模型让两者共享权重)。

这就是词表大小的真实取舍:**词表越大,同样文本的 token 数越少(省推理成本),但嵌入层和输出层越胖(占模型容量,也让每一步的 softmax 更贵)。** 现代模型的词表普遍在 32K 到 256K 之间,而扩大词表以更好支持多语言,是一个被反复讨论的工程决定。

## 练习

1. 用上面的实验测三段文本:一段你自己的中文写作、一段等价的英文翻译、一段你项目里的真实代码。记下三者的「字符/token」比。这三个数字以后会出现在你的每一次成本估算里。
2. 打开你正在用的模型的分词器(大多数都有在线可视化),输入你项目里最常出现的专有名词。它被切成了几段?如果超过三段,考虑在提示词里换一个更常见的说法,或者在微调数据里让它高频出现。
3. 估算:如果你的产品每天处理 5 万次请求、平均 1200 个输入 token,把用户输入从中文改成英文能省多少钱?然后想清楚为什么这个「优化」通常不该做。
