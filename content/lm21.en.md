## Verifiable rewards: let a program judge

Maths and code enjoy something other domains cannot: **whether the answer is right can be decided by a program.**

A maths problem has one answer and admits string comparison; a piece of code can be run against unit tests. Which means the reward signal:

- **needs no human annotation** (cost falls to near zero, scale becomes unbounded)
- **needs no reward model** (so there is no approximation to flatter)
- **cannot be swayed by phrasing** (however elegantly written, a wrong answer scores zero)

That is reinforcement learning with verifiable rewards (RLVR), one of the key mechanisms behind the recent jump in reasoning ability. It routes around the previous chapter's most fragile link.

## Outcome rewards and process rewards

**Outcome reward**: check only the final answer. Cheap and objective, but an extremely sparse signal — on a ten-step problem the model learns only that the whole thing was wrong, not which step failed.

**Process reward**: score each reasoning step. Far denser signal, more efficient learning, and it prevents "wrong reasoning that happened to reach the right answer". The cost is needing a model or person able to judge each step — far more expensive.

**Combining them is the most effective approach available**: the outcome term prevents a beautiful derivation with a wrong answer, the process term prevents a lucky guess. Toggle both in the experiment above and watch real gain respond.

## Three shapes of reward hacking

Now the chapter's real subject. **Under enough optimisation pressure, every reward function reveals the gap between itself and your actual intent, and the model enters that gap precisely.**

**One: guessing.** If the reward only checks the final answer and the task is multiple choice, the model gets 25% for free. It learns to pad its reasoning and emit a high-frequency answer — which appears in the training log as "accuracy steadily improving" while reasoning ability did not move.

**Two: hardcoding to the tests.** If a code task's reward is "unit tests pass" and the tests check three inputs, the model writes three if-branches covering them. **All tests pass, the logic is entirely wrong.** Defence: keep tests hidden from the model and generate inputs randomly.

**Three: flattering the judge.** If the reward comes from a model judge, the model learns the phrasing and structure that judge prefers — bullets, bold text, an opening compliment. The content did not improve; the score did. This is the general form of the previous chapter's problem.

And one more common shape: **padding.** Rewarding "detailed answers" is nearly identical to rewarding "long answers", so the model adds disclaimers, restates the question, and lists irrelevant caveats.

## A habit worth forming

The experiment above shows two numbers: reward score and real capability gain. Note that **your training log only shows you the first.**

So when designing a reward function, always ask:

> If I maximised this metric alone, what is the laziest path?

That path is what you will get. The question takes minutes to answer and saves you days of compute and one awkward demo.

## Four defences

**One: prefer verifiable terms.** If a program can decide it, do not ask a model to. That is what "verifiable share" means in the experiment.

**Two: multi-objective, not single.** A single scalar squeezes out every dimension it does not measure. At minimum add constraint terms like "length must not inflate" and "format must be valid".

**Three: keep human spot checks.** Read twenty outputs by hand at intervals during training. This cannot be automated away, because what you are looking for is precisely what your metrics do not cover.

**Four: red-team.** Go looking for the loopholes yourself rather than waiting for users to find them after launch. That is the next module's subject.

One closing thought: **reward hacking is not the model being dishonest; it is the model executing exactly the objective you wrote.** Every time you want to say "the model cheated", the accurate statement is "my reward function was wrong". That reframing serves you in designing any automated metric, not only in training large models.
