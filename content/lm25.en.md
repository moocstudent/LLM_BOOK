## An inference that goes wrong every day

"It's a 6B model, roughly 12GB at bf16, and I have 16GB of RAM — that should run, right?"

Three mistakes hide in that sentence, and they compound. First, 16GB is *total* memory, not the memory you can use. Second, "doesn't fit" does not produce a clean error in modern frameworks; it silently degrades into a mode a thousand times slower. Third, even when it does fit, how fast it runs is an entirely separate question, decided by bandwidth rather than clock speed.

This chapter is anchored on a real measurement: a laptop with an i5-12450H, 15.7GB of LPDDR5-5200 and no discrete GPU, running ChatGLM3-6B, produced **13 tokens in 629.3 seconds** — 48.4 seconds per token. The same model on an RTX 3090 runs at 30–40 tokens per second. Three orders of magnitude, and CPU compute explains only a sliver of it.

## Number one: available memory, not total memory

Measured on that machine: 15.73GB total, and Windows reported **4.85GB available**. With a browser and a few editors open it dropped further, at one point to 1.70GB.

The telling detail is that no single process was a memory hog — the largest was 0.39GB. Those 11 missing gigabytes were consumed by dozens of small processes, kernel allocations and non-reclaimable cache together. This is the normal state of a modern desktop, not a pathology.

Hence the first discipline: **estimate against available memory, then subtract runtime overhead.** The Python interpreter, the PyTorch runtime, activations and the KV cache together usually want 1–2GB.

```
space actually available for weights
  = available memory − 1.5GB (runtime)
  = 4.85 − 1.5
  = 3.35 GB
```

The weights need 12GB. That is a shortfall of 8.65GB — not a near miss, a factor of three.

## Number two: what happens when it does not fit

An outright OOM would be a kindness: you would know immediately to change plan. The real trouble is `device_map="auto"`.

That parameter exists to shard a large model across several GPUs. But when accelerate finds the memory insufficient, it does not fail — it **leaves the overflow weights on disk**, holds their place with meta-device tensors, and reads them back when the forward pass needs them. The model "loads successfully", accompanied by one understated line:

```
Some parameters are on the meta device because they were
offloaded to the disk and cpu.
```

And then **every generated token re-reads those weights from disk**. Autoregressive decoding traverses all layers at every step, so this cost is paid per token, not once.

### Three symptoms

**One: that offload notice.** It is unremarkable amid a wall of loading logs, and it is the single most important line there.

**Two: loading is implausibly fast.** The measured log reads "7 shards, 11.6GB, loaded in 6 seconds". No SATA SSD sustains 2GB/s; NVMe can approach it but not casually. The explanation is simple: **it never read them**. Fast loading is bad news, not good news.

**Three: the first token takes forever, and the spacing between tokens is even.** A compute bottleneck gives you steady slowness; offloading gives you steady, extreme slowness whose rhythm tracks disk speed.

## Number three: the ceiling bandwidth imposes

Suppose the memory problem is solved and every weight is resident. What is the speed limit?

Single-stream decoding (batch = 1) is **memory-bandwidth bound**: each generated token reads the entire weight set once, and each weight participates in exactly one multiply-accumulate. Arithmetic intensity is close to 1, which means additional compute buys nothing — the bottleneck is the trip from memory to the arithmetic units.

```
decode ceiling ≈ effective memory bandwidth ÷ weight size
```

That laptop has LPDDR5-5200 on a 128-bit bus: roughly 83GB/s theoretical, 50–60GB/s achievable. Substituting:

```
55 GB/s ÷ 12 GB ≈ 4.6 tokens/s
```

**That is a ceiling, not an expectation.** Discount it further: Alder Lake has AVX2 and AVX-VNNI but neither AVX-512 nor AMX, so PyTorch converts bfloat16 up to fp32 before multiplying — you pay half the bandwidth but collect none of the matching compute speedup. Reality lands nearer 1–2 tokens/s.

Compare an RTX 3090 at 936GB/s: `936 ÷ 12 ≈ 78`, against 30–40 measured — the same logic. **A GPU is fast first because its memory bandwidth is an order of magnitude higher, and only second because of its compute.**

This is also why batching matters so much server-side: read the weights once, serve the whole batch, and arithmetic intensity rises linearly with batch size. A single local conversation collects none of that dividend.

## Taking the 48.4 seconds apart

Back to the measurement. Below is an attribution built on the model above — note that this is a decomposition inferred from the measured total and known parameters, not four independent measurements:

| Component | Size | Rate | Time |
|---|---|---|---|
| Weights resident in RAM | ≈ 3.35 GB | ≈ 55 GB/s | ≈ 0.06 s |
| Weights offloaded to disk | ≈ 8.28 GB | ≈ 0.17 GB/s (inferred) | ≈ 48.3 s |
| **Total** | 11.63 GB | | **48.4 s** |

The inferred 0.17GB/s sits far below NVMe sequential read because the access pattern is not sequential streaming at all: accelerate pulls layers on demand, each with its own seek, deserialization and tensor reconstruction overhead, nowhere near nominal bandwidth.

The conclusion is stark: **99.9% of those 48.4 seconds went to disk.** The CPU spent essentially the whole time waiting. That measurement measured a hard drive, not compute.

## A decision procedure: compute before you download

Before typing `git clone`, walk these three steps:

1. **Compute the weight size.** Parameters × bytes per parameter. bf16/fp16 is 2 bytes, int8 is 1, int4 is 0.5. 6B × 2 = 12GB.
2. **Check available memory.** Not total. On Windows read "Available" in Task Manager; on Linux the `available` column of `free -g`. Subtract 1.5GB of runtime overhead.
3. **Compare, then compute the ceiling.** If it fits, bound the speed with bandwidth ÷ size. If it does not, change plan — do not expect the framework to rescue you.

The sandbox above turns those three steps into draggable form. Try sweeping "memory used by other programs" from 2GB to 10GB and watch where the "fits" verdict flips — it flips considerably earlier than intuition suggests.

## When the arithmetic says no

In increasing order of cost:

**Drop precision.** int4 quantization compresses 6B to about 3.7GB, which fits on an 8GB machine. But note that line 126 of ChatGLM3's bundled `quantization.py` carries a hard assertion requiring the weights to be on a CUDA device — **its quantization path does not support pure CPU**, and there is no workaround. Constraints like this are worth checking before you start.

**Change inference framework.** llama.cpp and Ollama use GGUF and are optimised for AVX2 without depending on AVX-512. The same int4 6B model typically reaches 5–8 tokens/s on comparable CPUs — conversational speed. The cost is leaving the transformers ecosystem, which makes the original repository's example scripts unusable.

**Change model size.** A 1.5B model needs only 3GB at bf16 and runs on most laptops. For many tasks a 1.5B that runs beats a 6B that does not.

**Do not run it locally.** If the task is quality-sensitive, an hour of rented GPU usually costs less than the time you spend avoiding that expense.

One closing note: those three numbers — weight size, available memory, bandwidth — take under two minutes to compute, while downloading 12GB of weights takes half an hour. **Compute first, download second.**
