## Four terms

"How large a model can my card fine-tune" is an addition with four terms:

```
VRAM = weights + gradients + optimizer state + activations
```

Term by term:

**Weights**: parameters × bytes per parameter. bf16 is 2 bytes; 4-bit quantization is 0.5 bytes plus a little scale-factor overhead. A 7B model in bf16 is 14 GB.

**Gradients**: only trainable parameters have them. Under full fine-tuning that is parameters × 2 bytes; under LoRA only 0.1%–1% of parameters are trainable and this term nearly disappears.

**Optimizer state**: the real reason full fine-tuning blows up memory. AdamW stores an fp32 first moment and an fp32 second moment per trainable parameter, **8 bytes** in total. For 7B that is 56 GB — three times the weights themselves.

**Activations**: the intermediate results saved during the forward pass for use in the backward pass. Proportional to `batch × sequence length × hidden × layers`, so at long sequences it becomes the largest term.

Add them up: **full fine-tuning a 7B model with AdamW needs roughly 14 (weights) + 14 (gradients) + 56 (optimizer) ≈ 84 GB, and with activations the commonly quoted figure lands near 100 GB.** That is where the number comes from — not a large model, a large optimizer.

## Which two terms LoRA removes

LoRA drops trainable parameters to about 0.2%, so gradients and optimizer state nearly vanish:

```
7B LoRA:  14 (weights) + 0.03 (grads) + 0.11 (optimizer) + activations ≈ 16-20 GB
```

**Note the weights term did not change** — the whole base model still sits in memory; you simply no longer store gradients and optimizer state for it. That is why LoRA can train 7B on a 24 GB card but not 70B (140 GB of weights alone).

QLoRA exists to address that remaining term.

## QLoRA's three key techniques

**One: NF4 quantization.** Quantize the frozen base weights to 4 bits. NF4 (4-bit NormalFloat) is a data type optimised for the prior that weights are approximately normally distributed — its quantization points are not uniformly spaced but placed at quantiles of a normal distribution, so the same 4 bits retain more information.

Crucially: **during backpropagation the 4-bit weights are dequantized to bf16 on the fly**, so gradient precision is not sacrificed; only the storage precision of the weights drops.

**Two: double quantization.** Quantization itself stores scale factors (one fp32 per 64 weights), and those add up. Double quantization quantizes them too, saving roughly another 0.4 bits per parameter.

**Three: paged optimizers.** Page optimizer state to host memory under pressure, avoiding OOM at peak moments.

Together: **QLoRA on 7B needs roughly 6–8 GB, and 70B roughly 40 GB — trainable on one card.** That is the change that moved large-model fine-tuning from the data centre to the desk.

The quality cost is usually one to two points, and training runs 20%–40% slower (dequantization has overhead).

## Four ways to save memory and what each costs

When you OOM, work in order of return:

| Lever | Saves | Cost |
|---|---|---|
| Switch to QLoRA | weights to 1/4 | 1–2 quality points, ~30% slower |
| Activation checkpointing | activations to ~1/6 | ~30% slower (recomputes forward) |
| Batch 1 + gradient accumulation | activations linearly | slightly slower, effective batch unchanged |
| Shorter sequences | activations linearly | may truncate your real inputs |

**Note the third: gradient accumulation lowers memory without changing the effective batch size.** That is nearly free and should be used first. Effective batch = batch × accumulation × devices, so batch 1 with accumulation 16 is mathematically equivalent to batch 16 with accumulation 1 (except for layers like BatchNorm, which Transformers do not have).

Those four steps usually fit 7B onto a single 24 GB consumer card.

## A check order worth memorising

When memory overflows, do not change parameters blindly. Compute the four terms first and see which dominates:

- **Optimizer state largest** → you are full fine-tuning; switch to LoRA.
- **Weights largest** → use QLoRA.
- **Activations largest** → enable checkpointing, lower the batch, shorten sequences.

The value of this order is that it avoids "fiddle until it starts" — an approach that often trades away effective batch size (hurting quality) just to get a run to launch.
