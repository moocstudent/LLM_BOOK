## Three tiers of reliability

To wire a model into a real system its output must be machine-parseable. Three tiers, with cost and effect both rising:

**Tier one: ask in the prompt.** "Output only JSON, no explanation." Measured validity runs around 70% — the model adds markdown fences, prefixes "Sure, here is the result", occasionally drops a quote.

**Tier two: schema plus validate-and-retry.** Supply a JSON Schema and, on a parse failure, feed the error back and ask for a correction. Validity exceeds 95%, at the cost of an occasional extra call (roughly 10% more latency and cost).

**Tier three: constrained decoding.** Mask, during decoding, any token that would make the JSON invalid — if the current state requires a string to begin, every token except `"` has its probability zeroed. Validity approaches 100% with no retries.

**Constrained decoding deserves emphasis**, because it converts "correct format" from a probabilistic problem into a deterministic one. Its mechanism is the same family as chapter one's attention mask: set illegal options' logits to -∞.

## Three lessons in schema design

**Fewer fields is better.** Every additional field is another place to fail. If your downstream does not use a field, delete it — do not keep it "in case".

**Flatter is better.** Three-level nested JSON has a significantly higher error rate than a flat structure. If it can be split into two calls, split it.

**Prefer enums wherever possible.** `"status": "active" | "expired" | "unknown"` is far more reliable than free text, and it incidentally solves hallucinated arguments — the model cannot emit a value outside the enum.

One more that gets overlooked: **give every field a legal "unknown" value.** If the schema requires `expiry_date` to be a date and the contract genuinely omits one, the model has two choices: invent one, or violate the schema. Adding `null` as legal turns "I don't know" into ordinary output rather than a failure.

## The tool-calling loop

Tool use is the natural extension: the model emits a function call rather than an answer. The loop looks like this:

```
think → call a tool → observe the result → think again → ... → answer
```

The experiment above walks you through it. Three things must be designed:

**Termination.** When does it stop? Normally when the model emits a final answer — but you must also set a hard turn limit (10, say), or an error the model cannot interpret produces infinite retries.

**Context management.** Every round's tool results accumulate in the context. After ten rounds the context may have swollen to tens of thousands of tokens, most of them irrelevant intermediates. You need a truncation or summarisation strategy.

**Permission boundaries.** The most important one — see below.

## Four failure modes

**One: hallucinated arguments.** The model invents a customer name absent from the database, the tool returns zero rows, and the model typically reads "zero rows" as "no data" rather than "my argument was wrong". **Defence: argument values should come from an enumerable list, not free generation.**

**Two: infinite loops.** As above; handled by turn limits and repeat-call detection.

**Three: empty results getting filled in.** When a query is valid and there genuinely is no data, the model is strongly inclined to invent a plausible number. **Defence: state in the prompt that empty results must be reported verbatim, and put a few empty-result items in your eval set.** These items are almost always omitted, and they are a common source of production incidents.

**Four: out-of-scope calls.** The model called `update_orders` instead of `query_orders`.

The fourth needs saying plainly: **permissions cannot be enforced by prompt.** "You may only query, never modify" is not a security boundary; it is a suggestion. The real boundary must live in the tool layer: expose only read-only tools to the model, and either withhold write operations or require human confirmation. This point recurs in module eight under prompt injection — **any security design that relies on the model's cooperation is not a security design.**

## Exercises

1. Inject each of the four faults in the experiment and write down the real scenario each corresponds to in your own system. Then check which ones your current implementation actually blocks.
2. Take one of your tool definitions and rewrite its schema against this chapter's three lessons: drop fields, flatten, replace free text with enums, add a legal unknown value per field. Rerun and compare the format-failure rate.
3. Audit your tool list: is any write operation exposed to the model without a human confirmation step? If so, that is the first thing to fix today.
