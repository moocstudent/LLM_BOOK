## Three metrics pulling against each other

Once live, you face three metrics that cannot all be optimal:

- **Quality**: pass rate, hallucination rate, format validity.
- **Latency**: time-to-first-token and total completion time. Users feel P95, not the mean.
- **Cost**: cost per call × volume.

Most teams' first instinct is to reach for a bigger model, which is the most expensive and crudest of the levers. The genuinely effective order is quite different.

## Optimisation order: start with the cheapest

**First, caching.** The only optimisation that leaves quality unchanged while lowering both latency and cost — free money.

The proportion of repeated requests in real traffic is often surprisingly high: FAQ-shaped questions, templated requests, user retries, scheduled calls from automated systems. If you have not measured your repeat rate, that is today's first task.

Caching has three levels worth separating: exact hits (identical input), semantic hits (vector similarity above a threshold — riskier, handle with care), and **prefix caching** (the KV cache for a shared system prompt can be reused — this one substantially reduces TTFT when system prompts are long, and it is lossless).

**Second, routing and cascading.** Let the fine-tuned small model carry the bulk, escalating the hard cases to a large one.

A well-designed two-tier system routinely buys 95% of the quality for 30% of the cost. This is also how module five's second reason to fine-tune pays off — you trained that small model for exactly this moment.

But mind the cascade's hidden cost: escalated requests **pay twice** (one small attempt plus the large call), and their latency is the sum of both. So the cascade's value depends on how much the small model resolves alone. **Below roughly two-thirds, hard routing by request type usually beats cascading** — because hard routing does not try first.

**Third, compress the prompt.** Tokens saved per call times volume. This is also fine-tuning's third legitimate reason.

Concretely: delete the ineffective politeness and role-play (module four measured it), bake stable examples into the weights, trim retrieved passages (lowering top-k often improves quality too).

**Fourth, and only then, change the model.** Note that it is last.

## Latency: optimise the two phases separately

TTFT and total duration respond to entirely different levers.

**TTFT** is set by prefill, which is proportional to input length. So shortening the prompt, using prefix caching, and retrieving fewer passages all improve it directly. Users are extremely sensitive to TTFT — past one second it starts to feel sluggish.

**Total duration** is set by output token count. So making the model say less (explicitly requiring brevity, dropping unnecessary chain-of-thought) is the most direct lever. Streaming does not change total duration but collapses perceived latency down to TTFT — **the highest-return front-end change available.**

## Four metrics to monitor after launch

**One: cost per call.** It creeps up quietly: rules keep getting added to the prompt, retrieved passages multiply, someone raises top-k from 3 to 10. Set an alert.

**Two: P95 latency.** Not the mean. The mean is dragged down by many fast requests while the experience is determined by the slow tail.

**Three: blended post-routing quality.** The "post-routing" matters: measure the complete system as routed with a single eval set, not the two models separately. A common incident is a mis-set routing threshold sending requests that should have escalated to careless handling by the small model — while each model's individual evaluation looks fine.

**Four: input distribution drift.** The most overlooked and the hardest to detect automatically. What users ask is changing while your fine-tuning data is a three-month-old snapshot. The method is plain: sample 50 live requests a week and read them by hand. **What you are looking for is "our eval set has nothing like this" — and no automated metric can find that.**

## Closing the loop

The course closes here.

In module one you learned to estimate training cost with `6ND`; here you estimate service cost with `tokens × price × volume`. Everything in the six modules between — pretraining data, decoding and quantization, prompting and retrieval, SFT data and hyperparameters, LoRA and VRAM, alignment and evaluation — is about finding an acceptable point between those two numbers.

If one sentence survives this course, let it be: **every technical choice converts into a number, and your job is to make sure that number gets computed rather than felt.**

1. In the sandbox, compute your monthly cost from your own real traffic (daily calls, average input and output lengths). Then enable caching and routing in turn, recording each saving. Take that number to your manager.
