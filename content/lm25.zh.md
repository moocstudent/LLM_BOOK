## 一个每天都在发生的错误推理

「这模型 6B,bf16 大概 12GB,我机器 16GB 内存——应该能跑吧?」

这句话里有三个错误,而且它们会叠加。第一,16GB 是**总**内存,不是你能用的内存。第二,「装不下」在现代框架里不会报错退出,它会静默降级成一种慢一千倍的模式。第三,就算装下了,能跑多快是另一个完全独立的问题,由带宽而不是 CPU 主频决定。

本章的锚点是一次真实测量:一台 i5-12450H、15.7GB LPDDR5-5200、没有独显的笔记本,跑 ChatGLM3-6B,**629.3 秒生成 13 个 token**——48.4 秒一个字。同一个模型在一张 RTX 3090 上是 30–40 token/秒。三个数量级的差距,而 CPU 算力只解释了其中很小一部分。

## 第一个数:可用内存,不是总内存

在那台机器上实测:总内存 15.73 GB,而 Windows 报告的**可用内存只有 4.85 GB**。开着浏览器和几个编辑器的时候更低,一度只剩 1.70 GB。

关键在于:没有任何一个进程是内存大户——占用最高的单个进程只有 0.39 GB。11 GB 是被几十个小进程、内核分配和不可回收的缓存一起吃掉的。这是现代桌面系统的常态,不是异常。

所以第一条纪律:**估算时用可用内存,并且减去运行时开销。** Python 解释器、PyTorch 运行时、激活值和 KV 缓存加起来通常要 1–2 GB。

```
真正可用于权重的空间 = 可用内存 − 1.5GB(运行时) 
                    = 4.85 − 1.5 
                    = 3.35 GB
```

而权重需要 12 GB。缺口 8.65 GB——不是差一点,是差了三倍。

## 第二个数:装不下的时候会发生什么

如果框架直接报 OOM 退出,反倒是好事:你立刻知道要换方案。真正的麻烦是 `device_map="auto"`。

这个参数的本意是把大模型切分到多张 GPU 上。但当 accelerate 发现内存装不下时,它不会失败,而是把放不下的那部分权重**留在磁盘上**,用 meta device 占位,等到前向传播需要时再读进来。于是模型「成功加载」了,你还会看到一句轻描淡写的提示:

```
Some parameters are on the meta device because they were
offloaded to the disk and cpu.
```

然后**每生成一个 token,那部分权重都要重新从磁盘读一遍**。自回归解码每步都要走完所有层,所以这个代价是每 token 都付一次,不是一次性的。

@fig lm25-offload

### 三个症状

**一,那句 offload 提示。** 它在一堆加载日志里毫不起眼,但它是最重要的一行。

**二,加载快得不合理。** 实测日志里写着「7 个分片、11.6 GB,6 秒加载完成」。任何 SATA SSD 都做不到 2 GB/s 的持续读,NVMe 勉强够但也不会这么轻松。答案很简单:**它根本没读**。加载快是坏消息,不是好消息。

**三,第一个 token 迟迟不来,而且每个 token 间隔均匀。** 如果是算力瓶颈,你会看到稳定的慢;如果是卸载,你会看到稳定的、极慢的、和磁盘速度成正比的节奏。

## 第三个数:带宽给出的天花板

假设内存问题解决了,权重全部驻留。速度上限是多少?

单条对话(batch=1)的解码是**内存带宽受限**的:每生成一个 token,都要把全部权重完整读一遍,而每个权重只参与一次乘加。算术强度接近 1,这意味着算力再强也没用,瓶颈在把权重搬到计算单元的路上。

```
解码速度上限 ≈ 有效内存带宽 ÷ 权重体积
```

那台笔记本是 LPDDR5-5200、128 位总线,理论带宽约 83 GB/s,实际可达 50–60 GB/s。代入:

```
55 GB/s ÷ 12 GB ≈ 4.6 token/s
```

**这是天花板,不是预期值。** 还要再打折扣:Alder Lake 支持 AVX2 和 AVX-VNNI,但没有 AVX-512 和 AMX,PyTorch 处理 bfloat16 时要先转成 fp32 再乘——省了一半带宽,却拿不到对应的计算加速。实际大约落在 1–2 token/s。

对比一下 RTX 3090 的 936 GB/s:`936 ÷ 12 ≈ 78`,实测 30–40,同样是这个逻辑。**GPU 快,首先是因为显存带宽快一个数量级,其次才是算力。**

@fig lm25-roofline

这也解释了为什么批处理在服务端如此重要:一次把权重读进来,可以同时服务整批请求,算术强度随批大小线性上升——但本地单人对话享受不到这个红利。

## 把 48.4 秒拆开

现在回到那次测量。下面是按上述模型做的归因(注意:这是基于测得的总时长和已知参数做的分解推算,不是逐项独立测量):

| 部分 | 体积 | 速度 | 耗时 |
|---|---|---|---|
| 驻留内存的权重 | ≈ 3.35 GB | ≈ 55 GB/s | ≈ 0.06 s |
| 卸载到磁盘的权重 | ≈ 8.28 GB | 反推 ≈ 0.17 GB/s | ≈ 48.3 s |
| **合计** | 11.63 GB | | **48.4 s** |

反推出来的 0.17 GB/s 远低于 NVMe 的顺序读速度,原因是这个访问模式根本不是顺序流式读取:accelerate 逐层按需加载,每层都有独立的寻址、反序列化和张量重建开销,吞吐远达不到标称带宽。

结论很清楚:**48.4 秒里有 99.9% 花在磁盘上。** CPU 几乎全程在等。这个测量测的不是算力,是硬盘。

## 决策表:先算再下载

在敲下 `git clone` 之前,先把这三步走完:

1. **算权重体积。** 参数量 × 每参数字节数。bf16/fp16 是 2 字节,int8 是 1,int4 是 0.5。6B × 2 = 12 GB。
2. **查可用内存。** 不是总内存。Windows 看任务管理器的「可用」,Linux 看 `free -g` 的 `available` 列。减去 1.5GB 运行时开销。
3. **对比,然后算天花板。** 装得下就用带宽 ÷ 体积估上限;装不下就换方案,别指望框架帮你兜底。

上面的沙盘把这三步做成了可拖动的形式。建议你把「其他程序占用」这一项从 2GB 拖到 10GB,看那条「装得下」的判定在什么位置翻转——你会发现它翻转得比直觉早得多。

## 如果算下来不行

按代价从低到高:

**降精度。** int4 量化把 6B 压到约 3.7GB,在 8GB 机器上也装得下。但要注意 ChatGLM3 自带的 `quantization.py` 第 126 行有一句硬性断言,要求权重必须在 CUDA 设备上——**它的量化路径不支持纯 CPU**,没有变通办法。这类限制要在动手前查清楚。

**换推理框架。** llama.cpp / Ollama 用 GGUF 格式,针对 AVX2 做了专门优化,不依赖 AVX-512。同样的 int4 6B 模型在同级别 CPU 上通常能到 5–8 token/s——可以正常对话的速度。代价是离开 transformers 生态,原仓库的示例脚本用不上。

**换模型规模。** 1.5B 在 bf16 下只要 3GB,大多数笔记本能直接跑。对很多任务来说,一个跑得动的 1.5B 胜过一个跑不动的 6B。

**别在本地跑。** 如果任务对质量敏感,租一小时 GPU 的钱通常低于你为了省这笔钱花掉的时间。

最后一句提醒:这三个数(权重体积、可用内存、带宽)算起来不到两分钟,而下载 12GB 权重要半小时。**先算,再下载。**
