## 三级可靠性

要把模型接进真实系统,输出必须能被程序解析。手段有三级,成本和效果同时递增:

**第一级:在提示里要求。** 「只输出 JSON,不要任何解释。」实测合法率大约七成——模型会加 markdown 代码块围栏、会在前面加一句「好的,这是结果」、偶尔会漏个引号。

**第二级:给 schema + 校验重试。** 提供 JSON Schema,解析失败就把错误信息回传给模型让它改。合法率能到九成半以上,代价是偶尔多一次调用(延迟和成本各加约 10%)。

**第三级:约束解码。** 在解码阶段直接屏蔽会导致非法 JSON 的 token——比如当前状态要求一个字符串开始,那么除了 `"` 之外所有 token 的概率都被置零。合法率接近百分之百,而且不需要重试。

**约束解码值得单独强调**,因为它把「格式正确」从一个概率问题变成了一个确定性问题。它的原理和第一章的注意力掩码是同一类:把非法选项的 logits 设成 -∞。

## schema 设计的三条经验

**字段越少越好。** 每多一个字段就多一处出错点。如果一个字段你的下游不用,删掉它——不要「先留着以后可能有用」。

**结构越平越好。** 三层嵌套的 JSON 的错误率显著高于扁平结构。能拆成两次调用就拆。

**能用枚举就用枚举。** `"status": "active" | "expired" | "unknown"` 比自由文本可靠得多,而且它顺便解决了幻觉参数问题——模型无法输出枚举之外的值。

再补一条容易被忽略的:**给每个字段一个「未知」的合法值。** 如果 schema 要求 `expiry_date` 必须是日期,而合同里确实没写,模型只有两个选择:编一个,或者违反 schema。加上 `null` 作为合法值,你就把「不知道」变成了一个正常输出而不是一次失败。

## 工具调用循环

工具调用是这件事的自然延伸:模型输出的不是答案,而是一次函数调用。循环长这样:

```
思考 → 调用工具 → 观察结果 → 再思考 → ... → 回答
```

上面的实验让你一步步走完这个循环。三个必须设计的点:

**终止条件。** 什么时候停?正常是模型输出了最终答案,但你必须同时设一个硬性轮次上限(比如 10 轮),否则遇到模型看不懂的错误时它会无限重试。

**上下文管理。** 每一轮的工具结果都会累积进上下文。跑十轮之后,上下文可能已经膨胀到几万 token,而其中大部分是无关的中间结果。需要有裁剪或摘要策略。

**权限边界。** 这是最重要的一条,见下节。

## 四类失败模式

**一,幻觉参数。** 模型编了一个数据库里不存在的客户名,工具返回 0 行,而模型往往把「0 行」解读成「没有数据」而不是「我的参数错了」。**防御:参数值应该来自可枚举列表,而不是自由生成。**

**二,死循环。** 见上文,靠轮次上限和重复调用检测。

**三,空结果被填空。** 查询合法但确实没数据时,模型有强烈的倾向去编一个合理的数字。**防御:在提示里明确「空结果必须原样报告」,并在评估集里专门放几条空结果样本。** 这类样本几乎总是被遗漏,而它们是生产事故的常见来源。

**四,越权调用。** 模型调用了 `update_orders` 而不是 `query_orders`。

第四条需要说得很清楚:**权限不能靠提示词约束。** 「你只能查询,不能修改」这句话不是一道安全边界,它只是一个建议。真正的边界必须在工具层:只把只读工具暴露给模型,写操作要么不暴露,要么要求人工确认。这一点在模块八讲提示注入时会再次出现——**任何依赖模型自觉的安全设计都不是安全设计。**
